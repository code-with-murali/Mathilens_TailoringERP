## [Unreleased]

### Added

- Initial repository structure (docs, prompts, src, tests, scripts, assets, docker, CI workflows) prepared for enterprise product development.
- Solution scaffolding: Clean Architecture .NET solution (`MathilensERP.Domain`, `.Application`, `.Infrastructure`, `.Api`, `.Shared`, `.UnitTests`, `.IntegrationTests`) with project references enforcing the documented dependency rules ([01_ARCHITECTURE.md § 6](docs/01_ARCHITECTURE.md#6-dependency-diagram)). Swagger via Swashbuckle per the documented API standard.
- Shared kernel (`MathilensERP.Shared`): `Result`/`Result<T>` and `Error`/`FieldError` types for modeling expected business outcomes without exceptions, `Guard` clauses for Domain invariant enforcement, and `PaginationDefaults` constants — with unit test coverage.
- Domain base entity (`MathilensERP.Domain.Common.AuditableEntity`): standard audit footprint (created/modified/deleted by+when) and soft delete, per 02_DATABASE.md §§ 5-6. Concurrency is deliberately handled at the Infrastructure/EF Core level (PostgreSQL `xmin`), not in Domain.
- Database foundation: EF Core `ApplicationDbContext` targeting PostgreSQL exclusively (`Npgsql.EntityFrameworkCore.PostgreSQL`), ASP.NET Core Identity (`ApplicationUser`/`ApplicationRole`) extended with the standard audit/soft-delete footprint, a `RefreshToken` domain entity for JWT rotation, a centralized soft-delete global query filter and audit-stamping `SaveChanges` interceptor, and the `InitialCreate` Code First migration. Identity's default `AspNetXxx` tables renamed to match 02_DATABASE.md's naming standard (`Users`, `Roles`, `UserRoles`, `UserClaims`, `UserLogins`, `UserTokens`, `RoleClaims`, `RefreshTokens`). 34 unit tests passing.
- Application layer foundation: a small hand-rolled in-process mediator (`ISender`, `ICommand`/`IQuery`, `IPipelineBehavior`) implementing 01_ARCHITECTURE.md § 25.3 without a third-party dependency, plus a FluentValidation-backed `ValidationBehavior` implementing § 11 Validation Strategy. `AddApplication()` registers handlers/validators via assembly scanning, per 00_MASTER_SPEC.md § 16.2.
- Authentication use cases: `LoginCommand` and `RefreshAccessTokenCommand` (Application) with validators, dispatched through `IIdentityService` (a port kept free of ASP.NET Core Identity's concrete types) implemented by `IdentityService` (Infrastructure) — JWT access token issuance, opaque refresh tokens (only the hash persisted), single-use rotation, and replay detection that revokes all of a user's active tokens, per 00_MASTER_SPEC.md § 10.1 / 01_ARCHITECTURE.md § 17. 51 unit tests passing.
- Api layer: `AuthController` (`POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`) and a protected `GET /api/v1/users/me` proving JWT bearer enforcement; `ApiControllerBase` maps `Result`/`Result<T>` to the standard success/error envelope (00_MASTER_SPEC.md § 8.6-8.7) including `ErrorType` → HTTP status mapping; `GlobalExceptionHandler` (§ 13 Exception Strategy) ensures no unhandled exception ever reaches a client as a raw stack trace; JWT bearer authentication middleware, Swagger with a bearer-token security definition, and XML doc comments surfaced in Swagger UI. Verified end-to-end via a local smoke test and 5 new `WebApplicationFactory`-based integration tests covering the paths that don't require a live database (validation failures, missing/malformed bearer tokens) — all passing. 56 tests passing total.
- Next.js dashboard shell (`web/`): login page against the auth API, a JWT-backed authenticated dashboard shell with sign-out and a dark/light theme toggle, and a thin fetch client matching the API's response envelope. CORS wired on the Api for the frontend's configured origin.
- GitHub Actions CI (`.github/workflows/ci.yml`): parallel `.NET build & test` and `Frontend lint & build` jobs on every push/PR to `main`.
- Customer Management backend (Phase 2's first module, 02_DATABASE.md § 10.3): `Customer` domain entity (`Domain/Customers`) enforcing full name + phone number as required invariants; EF Core configuration, `AddCustomers` migration, and a `CustomerRepository` (`Infrastructure/Persistence/Customers`) implementing the `ICustomerRepository` port (01_ARCHITECTURE.md § 25.1 Repository Pattern) with `SaveChangesAsync` exposed directly on it per § 25.7 (no separate Unit of Work abstraction). Application layer: `CreateCustomerCommand`, `UpdateCustomerCommand`, `DeleteCustomerCommand` (soft delete), `GetCustomerByIdQuery`, and a paginated `SearchCustomersQuery` (free-text over name/phone, using PostgreSQL's `ILIKE` via `EF.Functions.ILike`) — all with FluentValidation validators. A new `PagedResult<T>` (Shared) and `PaginationMeta`/`ToPagedActionResult` (Api) generalize the § 8.3 pagination envelope for future list endpoints. `CustomersController` (`/api/v1/customers`, `[Authorize]`-protected) exposes Create/GetById/Search/Update/Delete. 28 new unit tests (entity invariants, handlers, validators) plus 7 new integration tests (auth-gate and validation-error paths, following the same no-live-database-yet pattern as the Auth module's integration tests) — 91 tests passing total.
- Measurement Management backend (Phase 2's second module, 02_DATABASE.md §§ 10.4-10.5): `Measurement` (the current, active set for a customer + garment type) and `MeasurementHistory` (immutable snapshots, `IAuditable` directly rather than `AuditableEntity` — not soft-deletable, matching RefreshToken's precedent) domain entities in `Domain/Measurements`, plus a `GarmentType` enum (Shirt, Trousers, Suit, Blazer, Kurta, Blouse, Dress, Other). **Design decision**: measurement points are a flexible name/value set (`IReadOnlyDictionary<string, decimal>`, persisted as an ordinary JSON-text column, not a provider-specific JSON column type) rather than fixed per-garment-type properties — 02_DATABASE.md § 10.4 Future Expansion explicitly scopes "garment-type-specific measurement templates" as future work, so hardcoding columns per garment now would be exactly the speculative complexity YAGNI (00_MASTER_SPEC.md § 4.5) rules out; values are assumed centimeters by shop convention pending a real unit requirement. `AddMeasurements` migration; `MeasurementRepository` implementing `IMeasurementRepository`. Application layer: `CreateMeasurementCommand` (404 if the customer doesn't exist, 409 if a measurement for that customer+garment type already exists), `UpdateMeasurementValuesCommand` (snapshots the pre-update values into `MeasurementHistory` before applying the change), `GetMeasurementByIdQuery`, `GetMeasurementsByCustomerQuery` (unpaginated — bounded by the small, fixed `GarmentType` set), and a paginated `GetMeasurementHistoryQuery`. `MeasurementsController` (`[Authorize]`-protected; customer-nested routes for create/list, flat routes for by-id/update/history) exposes all five. 34 new unit tests plus 5 new integration tests — 125 tests passing total.
- Employee Management backend (Phase 2's third module, 02_DATABASE.md § 10.6): `Employee` domain entity (`Domain/Employees`) with full name required, job title/phone/email optional, and a nullable `UserId` reserved for the documented optional one-to-one link to a system login. That link is schema-only for now — `EmployeeConfiguration` wires a real FK to `ApplicationUser` plus a filtered unique index (`WHERE "UserId" IS NOT NULL`) so the constraint exists in the database, but no command in this module sets `UserId` yet, since linking an employee to a login account is the same admin/role-management flow Phase 1 already deferred pending a live database. `AddEmployees` migration; `EmployeeRepository`. Application layer mirrors Customer Management: `CreateEmployeeCommand`, `UpdateEmployeeCommand`, `DeleteEmployeeCommand` (soft delete), `GetEmployeeByIdQuery`, paginated `SearchEmployeesQuery`. `EmployeesController` (`/api/v1/employees`, `[Authorize]`-protected). 22 new unit tests plus 5 new integration tests — 156 tests passing total.
- Tailoring Orders + Fabric Details backend (Phase 2's fourth and fifth modules, built together, 02_DATABASE.md §§ 10.7-10.8, 10.11): `Order` is the aggregate root — `Domain/Orders` — owning a collection of `OrderItem`s (each with an optional one-to-one `FabricDetails`), all only ever created/modified through `Order`'s own public methods (`AddItem`, `SetItemFabric`, `AssignEmployee`, `TransitionTo`), never independently; both child types have `internal` factory methods enforcing that. **Design decision — order lifecycle**: a strict, enforced state machine per 02_DATABASE.md § 10.7's own example ("cannot move to Delivered without passing through In Progress") — `Received → InProgress → ReadyForDelivery → Delivered`, with cancellation allowed from any non-terminal state, both terminal. Every mutating command checks `Order.CanTransitionTo`/`CanModifyItems` *before* calling the mutating method, converting an invalid attempt into a clean `409 Conflict` rather than an unhandled exception (01_ARCHITECTURE.md § 13). `AddOrders` migration, including real FKs from `Orders` to `Customers`/`Employees` and cascade-owned `OrderItems`/`FabricDetails`; `OrderRepository` (always eager-loads the full aggregate). Application layer: `CreateOrderCommand` (creates an order with its initial items/fabric in one call — validates the customer and, if provided, the assigned employee both exist), `AddOrderItemCommand`, `SetOrderItemFabricCommand`, `TransitionOrderStatusCommand`, `AssignOrderEmployeeCommand`, `GetOrderByIdQuery`, and a paginated, customer/status-filterable `SearchOrdersQuery`. `OrdersController` (`/api/v1/orders`, `[Authorize]`-protected) exposes all of it. 41 new unit tests plus 6 new integration tests — 210 tests passing total. **This completes Phase 2's backend** (Customer, Measurement, Employee, Orders/Fabric Details).
- Billing backend (Phase 3's first module, 02_DATABASE.md §§ 10.9-10.10): `Invoice` is the aggregate root — `Domain/Billing` — owning a collection of `Payment`s (`IAuditable` directly, not `AuditableEntity`, matching `MeasurementHistory`/`RefreshToken`'s precedent for insert-only, never-edited records), only ever created through `Invoice.RecordPayment`. **Design decision — Order relationship**: kept 02_DATABASE.md § 10.9's stated default (many-to-one: an order may accumulate more than one invoice over time, each invoice bills exactly one order) rather than building many-to-one-spanning-multiple-orders, which the doc explicitly frames as this module's decision to make, not a requirement. **Design decision — status**: `Unpaid → PartiallyPaid → Paid`, or `Void`, recomputed automatically by `RecordPayment` from `AmountPaid` vs. `TotalAmount` — never set directly, so it can't drift from the payment history. Voiding is only allowed on an invoice with zero payments recorded (`CanVoid`); a partially/fully paid invoice needs a documented credit/adjustment process that isn't built yet (02_DATABASE.md § 10.9's "not an in-place edit of a settled invoice" — scoped out of V1, noted as a gap below). `AddBilling` migration, with real FKs from `Invoices` to `Orders`/`Customers`; `InvoiceRepository`. Application layer: `CreateInvoiceCommand` (computes `Subtotal` from the order's items, validates the order exists and has items, and that the discount doesn't zero out or exceed the total), `RecordPaymentCommand`, `VoidInvoiceCommand`, `GetInvoiceByIdQuery`, and a paginated, customer/status-filterable `SearchInvoicesQuery`. `InvoicesController` (`/api/v1/invoices`, `[Authorize]`-protected). Invoicing is a deliberate, explicit staff (or future automation) action rather than an automatic side effect of an order reaching `Delivered` — there's no domain-event dispatch mechanism wired up yet (01_ARCHITECTURE.md § 26 Future Event-Driven Architecture is exactly that, future). 40 new unit tests plus 6 new integration tests — 250 tests passing total.

- WhatsApp backend (Phase 3's second module, 00_MASTER_SPEC.md § 3 / § 5): `WhatsAppMessage` (`Domain/WhatsApp`) is a persisted log entry per send attempt — `Pending` at creation, then `Sent`/`Failed` — for auditability and delivery-status tracking (01_ARCHITECTURE.md § 11.5: "failures are logged and surfaced"). **Provider choice**: Meta's WhatsApp Cloud API, called directly (the user's explicit decision over Twilio), behind an `IWhatsAppSender` port (`Application/Common/Interfaces`) so the product isn't locked to that specific provider (01_ARCHITECTURE.md § 28 Risks). `MetaWhatsAppSender` (`Infrastructure/WhatsApp`) is a typed `HttpClient` matching Meta's documented `POST /{api-version}/{phone-number-id}/messages` contract — **unverified against a live account**: no real Meta Business/WhatsApp Business Account credentials have been available in this environment, so it has never actually sent a message. `WhatsAppOptions` is deliberately *not* required-on-start (unlike `JwtOptions`) — the API must start cleanly without WhatsApp configured, and `MetaWhatsAppSender` returns a graceful `Failed` result per-send when credentials are missing, rather than throwing. `AddWhatsAppMessages` migration, with real FKs to `Customers`/`Orders` (the latter nullable — not every message is order-related). Application layer: `SendWhatsAppMessageCommand` (persists the message as `Pending` in its own commit, calls the sender, then commits the final status in a second commit — deliberately two transactions, not one spanning the external HTTP call), `GetWhatsAppMessageByIdQuery`, and a paginated, customer/order/status-filterable `SearchWhatsAppMessagesQuery`. `WhatsAppMessagesController` (`/api/v1/whatsapp-messages`, `[Authorize]`-protected). Sending is an explicit action, same as Billing's invoicing, for the same domain-event-dispatch-doesn't-exist-yet reason (01_ARCHITECTURE.md § 26 describes it as already active — "Now:" — but no code in this project actually implements it; this is a pre-existing gap this module doesn't retrofit). 24 new unit tests plus 5 new integration tests — 274 tests passing total. Per this codebase's established precedent (repositories are never unit-tested directly, only through their ports via mocked interfaces), `MetaWhatsAppSender` itself has no direct unit test either — only `IWhatsAppSender` consumers do.

### Known Gaps

- None of Phase 2's five modules, Billing, or WhatsApp has a frontend UI yet (Next.js pages) — per 00_MASTER_SPEC.md § 15 Definition of Done, none is "complete," only their backends are.
- No PostgreSQL instance (local, Docker, or otherwise) has been available in the development environment to date, so no code in this project has been run against a live database yet. Every "passing" test suite exercises fail-fast/validation paths ahead of the database, by design (see `CustomWebApplicationFactory`'s doc comment). This is the single biggest risk across everything built so far: the EF Core model (relationships, conversions, indexes) has never actually round-tripped against real PostgreSQL, only been validated by `dotnet ef migrations add` successfully building the model and generating SQL that reads as correct on inspection.
- Billing's credit/adjustment process for correcting a partially/fully paid invoice (02_DATABASE.md § 10.9) is not built — only voiding an invoice with zero payments is supported.
- WhatsApp's `MetaWhatsAppSender` has never sent a real message — no Meta Business/WhatsApp Business Account credentials have been available to test against.
- 01_ARCHITECTURE.md § 26's domain-event dispatch mechanism ("Now: ... dispatched in-process ... via the mediator") is described as already active but isn't actually implemented anywhere in this codebase — Billing's invoicing and WhatsApp's sending are both explicit commands as a result, not automatic reactions to an order status change, which is what the architecture doc's own example (order completion triggering billing/WhatsApp) describes.

### Documentation

- 02_DATABASE.md: added the `RefreshTokens` entity (§ 10.14), discovered as a genuine implementation-time gap — the refresh-token rotation behavior was specified but its storage wasn't enumerated in the original 13-entity list.
- 00_MASTER_SPEC.md § 5 Technology Stack: dropped FluentAssertions from the Testing row — its license became commercial-only starting v8, an unacceptable risk for a product built to be sold. xUnit's built-in `Assert` (already in use) plus NSubstitute cover the same need at no licensing risk. Recorded as an explicit amendment per the document's own precedence rules.
